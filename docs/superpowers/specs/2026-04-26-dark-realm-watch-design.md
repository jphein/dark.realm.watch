# dark.realm.watch — design spec

**Date:** 2026-04-26
**Status:** Approved (pending implementation plan)
**Realm:** void (per realm-sigil convention)
**License:** MIT

## What this is

A drop-in include for system-aware dark/light theming. Web (HTML/CSS/JS) plus a Linux CLI for shell scripts and GNOME extensions. Schema-agnostic: it manages the *attribute and the user preference*, not the colors. Consumers bring their own CSS variables.

## Why this exists

JP's projects already implement dark/light theming twenty different ways. Two of the most evolved (`portfolio`, `disks`) have independently converged on the same canonical pattern — `data-theme` attribute + a `:not([data-theme="dark"])` system fallback — but each reimplements the engine, none have a no-FOUC blocking head script, and none expose a clean three-state (light/dark/system) preference. Tier-1 projects (`clock`, `opus`, `familiar`, `lettertomom`, `artcardsv5`...) only do the CSS half and have no toggle at all.

This package extracts the *correct* pattern, ships it as layered drop-in files, and provides an opt-in custom-element toggle so projects can stop reinventing.

The Linux CLI exists because JP's GNOME extensions, daemons, and shell scripts need to react to system theme changes; the cross-desktop standard for this (`org.freedesktop.appearance / color-scheme` on the XDG Desktop Portal) is awkward to call directly. A `dark` / `dark watch` script collapses it to one line.

## Non-goals

- **No npm package.** Drop-in includes shouldn't need a build step.
- **No Python/Go/native modules.** Linux CLI is shellable from any language.
- **No `<meta name="theme-color">` management.** Project-specific colors don't belong in a generic include; consumers handle their own browser-chrome color.
- **No auto-switching by sunrise/sunset.** That's [Night Theme Switcher](https://extensions.gnome.org/extension/2236/night-theme-switcher/)'s job; the README will link to it.
- **No GTK/Qt theme *management*.** We *read* the system preference; we don't *set* it.
- **No imposed CSS variable schema.** JP's existing projects use incompatible naming (`--bg`, `--bg-surface/--bg-elevated`, `--bg-void`, `--bg-warm`...). The include must work with all of them.

### Three layered tiers of consumer adoption

| Tier | Files used | What the consumer ships |
|---|---|---|
| 1 — CSS-only, system-following | `dark.css` | One link tag. Their own CSS vars in the existing selectors. No JS. |
| 2 — JS engine, custom toggle UI | `dark.css` + `dark-head.js` (inline) + `dark.js` | Wire their own button to `Dark.cycle()`; listen for `dark:change`. |
| 3 — JS engine + default toggle UI | All four web files | `<dark-toggle>` or `<dark-toggle variant="pills">` tag. |

Each tier strictly extends the previous. A project starts at tier 1 and grows into tier 2 or 3 without changing existing CSS.

## Web components — detailed design

### `dark.css` — selector preset

```css
:root[data-theme="light"] { color-scheme: light; }
:root[data-theme="dark"]  { color-scheme: dark; }
@media (prefers-color-scheme: light) {
  :root:not([data-theme="dark"]) { color-scheme: light; }
}
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { color-scheme: dark; }
}
```

**Three-state contract:**
- `data-theme="light"` → explicit light, persisted
- `data-theme="dark"` → explicit dark, persisted
- attribute *absent* → follow system (`prefers-color-scheme` decides)

The `color-scheme:` declaration tells the user agent to use dark form controls / scrollbars / autofill backgrounds. It is the bit most ad-hoc implementations miss.

Consumers add their own variables by repeating the same selectors:

```css
/* consumer's stylesheet */
:root { --bg: #0a0a0c; --fg: #eeeeee; }
:root[data-theme="light"] { --bg: #f5f5f7; --fg: #111; }
@media (prefers-color-scheme: light) {
  :root:not([data-theme="dark"]) { --bg: #f5f5f7; --fg: #111; }
}
```

The README documents this pattern with a copy-paste template. Optional helper: a CSS that uses `light-dark()` and a single `:root { color: light-dark(black, white); }` block — works in modern browsers and is shorter, but only handles the system case (no manual override). Not the default; documented as an alternative for tier-1 projects targeting modern browsers only.

### `dark.js` — the engine

Public API:

```js
Dark.current()           // 'light' | 'dark' | 'system' — user's stored preference
Dark.effective()         // 'light' | 'dark' — what's actually showing right now
Dark.set(value)          // value in {'light','dark','system'}; persists or clears storage
Dark.cycle()             // system → dark → light → system → ...
Dark.config({ storage })  // override storage key (default 'drw-theme')
```

Behavior:
- On load, reads localStorage (key `drw-theme` by default). If `light` or `dark`, sets `data-theme` accordingly. If absent or `system`, removes the attribute (CSS handles the rest).
- Subscribes to `window.matchMedia('(prefers-color-scheme: dark)')` `change` events. Re-applies only when `Dark.current() === 'system'`.
- On `Dark.set('system')`, removes the localStorage key (so absence = system; storage is canonical).
- Dispatches `dark:change` on `document` after every change, with `detail: { theme: 'light'|'dark'|'system', effective: 'light'|'dark' }`.
- No globals beyond `window.Dark`. No dependencies.

Cycle order rationale: starting from `system`, the most common next user action is "I want this dark" (dramatic flip). From dark, the alternative is light. From light, the user has tried both manual states and the next sensible step is "back to system." Hence: system → dark → light → system.

Storage key (`drw-theme`) is namespaced to avoid collision with existing project-specific keys (`disks`'s `vault-theme`, etc.). Override via `Dark.config({ storage: 'mykey' })` before any other `Dark` call, or via `data-dark-storage="mykey"` attribute on the script tag.

### `dark-head.js` — render-blocking, no-FOUC

The canonical use is to **inline** this in `<head>` *before any stylesheet link*:

```html
<script>(()=>{const s=localStorage.getItem('drw-theme');if(s==='dark'||s==='light')document.documentElement.setAttribute('data-theme',s)})()</script>
```

~120 bytes. Reads localStorage synchronously, sets the attribute before paint. Solves the disks/portfolio first-paint flash.

The repo also ships `dark-head.js` as a standalone file consumers can `<script src="..."></script>` if they prefer (slightly worse for FOUC because of the network round-trip, but acceptable for prototypes on `dark.realm.watch`'s own CDN).

If `Dark.config({ storage })` overrides the key, the consumer must edit the inlined snippet to match. README documents this with a one-line `sed`-able template.

### `dark-toggle.js` — opt-in custom element

```html
<dark-toggle></dark-toggle>                    <!-- icon variant (default); click cycles -->
<dark-toggle variant="pills"></dark-toggle>    <!-- three-pill variant -->
```

**Icon variant** (default):
- Single `<button>` inside the shadow root
- Glyph reflects `Dark.current()`: `☀` (light), `☾` (dark), `◐` (system)
- Click → `Dark.cycle()`
- Inherits `currentColor` and `font-size` from the host's environment

**Pills variant**:
- Three `<button>` elements (Light / Dark / System) in a row
- The one matching `Dark.current()` gets `aria-pressed="true"` and a `--active` style
- Click → `Dark.set('light'|'dark'|'system')`
- Layout uses CSS `inline-flex`, ~120px wide, also reskinnable via `currentColor` / `font-size`

Both variants:
- Listen for `dark:change` and update their own visual state, so multiple toggles on a page stay in sync
- Are accessible (proper button roles, `aria-label`, `aria-pressed` where applicable, focus styles)
- Only attach event listeners on `connectedCallback`; clean up on `disconnectedCallback`

Reskinning contract: setting `color`, `font-size`, or `--active-color` / `--inactive-color` on (or above) the `<dark-toggle>` element propagates into the shadow root via `currentColor` / `font-size` / CSS custom properties.

## Linux side — `linux/dark`

Single bash script, two modes:

```
dark             # prints "dark", "light", or "unknown" then exits 0 (or 1 for unknown)
dark watch       # streams "dark"/"light" lines on each system flip; runs until killed
dark --help      # usage + exit
```

**Reading the current theme:**
1. Try the cross-desktop standard via D-Bus:
   ```
   gdbus call --session --dest org.freedesktop.portal.Desktop \
     --object-path /org/freedesktop/portal/desktop \
     --method org.freedesktop.portal.Settings.Read \
     org.freedesktop.appearance color-scheme
   ```
   Map the returned variant: `1` → dark, `2` → light, `0` → unknown.
2. If `gdbus` fails or the portal isn't present, fall back to:
   ```
   gsettings get org.gnome.desktop.interface color-scheme
   ```
   Map: `'prefer-dark'` → dark, `'prefer-light'` → light, anything else → unknown.
3. If both fail, exit 1 with `unknown` printed to stdout.

**Watch mode:**
- Use `gdbus monitor --session --dest org.freedesktop.portal.Desktop` and grep for `SettingChanged` signals on the `org.freedesktop.appearance` namespace, key `color-scheme`.
- On each match, parse the new value and print `dark` or `light` followed by a newline (line-buffered).
- If the portal isn't available, fall back to `dconf watch /org/gnome/desktop/interface/color-scheme` for GNOME-only fallback.
- Exit on SIGINT/SIGTERM cleanly.

**Dependencies:** bash, `gdbus` (in `glib-2.0-bin` or `libglib2.0-bin` — present on virtually every modern Linux desktop). `gsettings` and `dconf` only used as GNOME-specific fallback.

**Install:** users symlink `dark` into `~/.local/bin/` or `/usr/local/bin/`. README documents both. The `linux/` subdirectory is intentional so future Linux helpers (e.g., a systemd user service that watches and triggers per-app theme reloads) can live alongside without polluting the root.

## Demo page — `index.html` (the URL itself)

Single-page fantasy showcase that uses the include to demo itself. Sections, top to bottom:

1. **Hero**: large SVG of a sun-and-moon split disc that morphs across the theme transition. CSS uses `light-dark()` for the fill. Animates smoothly when toggled.
2. **System indicator**: small pill near the hero — "Your system: dark" or "Your system: light" — proving the read worked.
3. **Both toggle variants visible and working**: icon top-right (always), three-pill below the hero. Both wired to the same `Dark` instance; clicking one updates the other (good demonstration of the event bus).
4. **Three code samples** with copy buttons:
   - "Drop in" — link `dark.css`, inline the head snippet, script tag `dark.js`
   - "Add a default toggle" — `<dark-toggle>` and `variant="pills"`
   - "Use from a script" — listen for `dark:change`, call `Dark.cycle()`
5. **Linux section**: install snippet for the `dark` CLI; a static example of `dark watch` output (no Linux env required to view the demo).
6. **Sigil version footer** (mandatory per JP's CLAUDE.md): generated by `realm-sigil/static/build.sh`.
7. **Favicon**: half-dark-half-light circle SVG matching the project metaphor.

The page itself respects the include — toggling on the demo page sets the user's `drw-theme` localStorage value, which any other site using the include will then inherit on the same origin (which is none, since `dark.realm.watch` is its own origin — but it demonstrates the pattern).

## Opinionated defaults

| Decision | Default | Rationale |
|---|---|---|
| Storage key | `drw-theme` | Namespaced to avoid collision; consumers override via `Dark.config({storage})` |
| Cycle order from system | system → dark → light → system | Most users who toggle want dark first; light second; back-to-system last |
| Theme attribute | `data-theme="light"` or `"dark"` (absent = system) | Already convention in `portfolio` and `disks` |
| Event name | `dark:change` on `document` | Concise, namespaced enough |
| `color-scheme` CSS prop | Always set in all four selectors | Critical for UA-controlled dark form widgets |
| Default toggle variant | `icon` | Disks-style, most common need; pills via `variant="pills"` |
| `<meta name="theme-color">` | Not handled in v1 | Project-specific; future enhancement |
| License | MIT | Matches `clock.realm.watch`, `realm-sigil`, etc. |

## Open questions / explicit future work

- **`theme-color` meta updates** — could be added later via `<dark-toggle theme-color-light="#fff" theme-color-dark="#000">` style attributes on the toggle. Out of v1.
- **Sub-resource integrity (SRI) hashes** for the CDN includes — future hardening once URLs stabilize.
- **A daemon companion** (`dark-watch.service`) that runs `dark watch` and triggers per-app reloads (tmux, neovim, GTK theme swap) — separate project, would consume this one's `dark watch`.
- **A small adopter migration guide** for the existing 20 projects: which CSS lines change, where to drop the head snippet, when to add the toggle. Lives in README, not v1 code.

## Success criteria

A new project can adopt dark/light theming in 3 lines (`<link>`, inlined head snippet, `<script>`). An existing project (e.g., `disks` or `portfolio`) can replace its hand-rolled engine with this include and gain the no-FOUC fix + the third "system" state without losing any current behavior. The Linux CLI returns the right answer on JP's primary GNOME desktop and remains correct after a `gsettings set ... color-scheme prefer-light` flip, with `dark watch` emitting one line within ~100ms.
